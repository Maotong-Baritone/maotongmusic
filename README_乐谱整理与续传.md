## 1. 用户已经确认的条目整理规则

### 1.1 标题、作品号与所属作品

- 沿用网站已有的简洁命名方式，保留可靠的原文作品名，不擅自给全部作品另造中文译名。
- 勃拉姆斯的标题必须带作品号，如 `Op. 116`；有具体曲号时带 `No. 1` 等。没有 Op. 号而有 `WoO`、`Anh.` 等目录编号时保留实际编号，不编造 Op. 号。
- 完整作品用总标题。独立单曲、乐章、选段、分册用实际内容的独立标题；“所属作品”字段保留总标题以便归组。
- 多首选段注明编号范围；不完整片段注明范围/片段编号；上下册或 Book I / Book II 不得同名。不能仅凭文件名中的数字猜乐章号。
- 长题辞、诗句、出版说明、校订说明放详情，不挤进标题或灰色标签。
- 完整作品的多个不同版本、分谱、钢琴缩编谱要能区分实际版本和文件范围，不能全部写成无法辨认的同名条目。

### 1.2 调性

- 有可靠依据才填写；不明时留空并记录疑点，不凭印象补齐。
- 使用现有中文写法，如 `C大调`、`降B大调`、`升f小调`、`d小调`、`a小调`，调性单列。
- 单曲写本曲调性，不能继承整套作品的调性。跨多个调性的曲集不要强行套一个调。
- 移调谱、高低声版本必须核对当前 PDF；常见原调不一定是这份谱子的调。
- 页面说明、标题和实际谱面有冲突时核实，详情写明差异和依据，不能悄悄修改原谱。

### 1.3 声部与编制：中文、简短、与这份文件相符

- `piano` 写“钢琴”；独奏钢琴谱可写“钢琴独奏”；声乐加钢琴写“声乐、钢琴”。
- 重唱写“二重唱、钢琴”“四重唱”等，或写清实际声部；不堆砌不必要的说明。
- 分谱写“小提琴分谱”等，钢琴缩编/伴奏文件按实际内容写“钢琴谱”等；总谱用“小提琴、管弦乐”“管弦乐总谱”等简写。
- 不在列表灰色标签中罗列“2支长笛、2支双簧管、4支圆号……”这种长编制。确有价值的完整配器放详情。
- 区分原作编制和当前 PDF 的实际编制，不能给钢琴改编谱贴一整串原作管弦乐编制。
- 简短不等于丢失必要区分：独奏/四手联弹/双钢琴、总谱/分谱/缩编谱等仍需准确表达。

### 1.4 分类、子分类和语言

- 优先沿用网站已有分类；确需新增分类时告诉用户，不自行扩充分类体系。
- 一级分类已经是“艺术歌曲”，后面不要再显示灰色“艺术歌曲”。法国艺术歌曲也不要额外标“香颂”；法语写在语言字段。
- 不新增“声乐重唱”分类。艺术歌曲的二重唱、四重唱等仍归“艺术歌曲”，靠中文编制说明几重唱或声部。
- 真正的合唱作品、宗教声乐、歌剧重唱等仍按实际内容放入现有相应分类，不把所有多人演唱都归艺术歌曲。
- 子分类保留有用的曲式信息，例如“器乐独奏”下面的“变奏曲”“奏鸣曲”，不是删除所有灰色分类标签。
- 无歌词的器乐作品，歌词语言字段留空，不写“无歌词”；网页若用 `-` 表示空值，不把它当成歌词语言存入。

当前后台允许的一级分类（以 `admin_tool.py` 中 `ALLOWED_CATEGORIES` 的实际定义为准）：歌剧咏叹调、歌剧重唱、宗教声乐作品、艺术歌曲、音乐剧选段、合唱作品、音乐会咏叹调/世俗康塔塔、声乐套曲、乐谱书/曲集、器乐独奏、器乐分谱、室内乐、歌剧总谱、管弦乐/交响曲、协奏曲总谱、宗教声乐作品总谱、其他。

### 1.5 完整曲集、目录与原文件

- 完整 PDF 保留来源原始字节，不自动拆谱、重排、删封面或广告；另有独立单曲 PDF 时，按独立标题收录。
- 多乐章/多首完整文件的详情补充内容目录及实际 PDF 起始页，便于寻找单个乐章。
- PDF 页码与谱面印刷页码分开说明；注意封面、校订报告、前言以及两个乐章同页开始的情况。
- 原谱误标时保留原文件，网站元数据使用核实后的信息并注明。例如已发布 Op.119 No.3 的 PDF 标题误写 A Minor，实际核实为 C大调，详情已说明。
- 来源文件本身经过滤处理时如实记录，不能称为“未经处理原始扫描”。已发布 Op.24 来源文件名含 `filter`，详情已标明，下载后未改动字节。

## 2. 审核方式：先确认规则，再集中处理疑点

用户不希望逐页审核上百页候选。已采用“代表性规则样例 → 按作品/版本分组 → 集中处理疑点 → 必要时逐文件编辑”的流程。

- 样例用于确认整理风格，不等于批准全部文件；“无警告”也不等于已经核对谱面。
- 分组批量修改仅适用于确实共享信息的文件。不同调性、乐器声部、改编者或文件范围不能机械套用同一字段。
- 暂缓保留记录，不删除；版本分组不合并、不删除 PDF。
- 只读批次报告应能看见：拟用标题、所属作品、调性、分类/子分类、中文编制、语言、文件范围/页数、来源链接/文件号、版本与许可、疑点及拟修改内容。
- 大规模变更规则时，先展示代表性样例和影响范围，避免发布后再大规模返工。
- 用户已确认当前风格并授权继续常规合格批次，不需每批重复询问。未解决的谱面疑点、新分类、特殊许可、排除项或冲突不因“都可以上传”而自动通过。

本地审核入口及各按钮含义见 [勃拉姆斯预审说明](imports/johannes_brahms/README.md)。审核修改的主清单是 `manifest.json`；`review_catalog.csv` 只是导出快照，修改 CSV 不会写回审核页面。

## 3. 下载、版本筛选与谱面检查

以下为已采用的执行流程；继续时保持这些质量检查，不把它们当成仅凭元数据就能跳过的步骤。

1. 优先在作品中选一份清晰完整版本，再补有用的独立单曲。不要把同版的重复扫描全部上传。
2. 依据 IMSLP 文件号、稳定的站内 `public_id` 和内容 SHA256 排查重复；不同调性/编制/版本不能只因同名就合并。
3. 作曲家本人改编可在核实后按实际版本整理；第三方或未确认改编保持当前待审/排除规则，不能批量解除限制。
4. 使用匿名正常流程，遵守站点等待时间、频率限制与许可条件。只用实际观察到且正常放行的下载地址；不猜隐藏地址，不绕过登录、付费、验证码、版权检查或工具安全停止。
5. 下载至隔离暂存目录，保留实际来源地址、文件号、文件名、出版/编订信息、许可说明、页数、文件大小和 SHA256。确认下载物真的是 PDF，而非网页或缩略图。
6. 解析文件结构并渲染所有页；检查完整性、标题/册号/单曲范围、各乐章起始页、调性和实际编制。按 PDF 技能的要求进行视觉核查，保留检查记录。
7. 元数据有错时记录修改前后值、依据、备份与并发校验，只修改本批明确的条目；不全局覆盖用户已经编辑过的资料。

## 4. 发布流程与完成标准

“下载完成”“已批准”“已上传 R2”“本地目录已写入”“网站已上线”是不同状态，不能混报。

1. 先读当前交接、审核清单及发布回执，核对本地/线上和 Git 状态；确认没有另一个任务同时写库或发布。
2. 若上批已写目录但尚未完成部署/验证，先收尾该批，再进行下一批正式目录写入。
3. 每次选择明确、有界的小批文件号；完成暂存核查、只读报告和发布预览，再执行正式写入。
4. 备份相关清单、公开 JSON 和数据库。仅上传本批文件；遇远端同键不同内容停止处理，不覆盖冲突对象。
5. 逐份公开下载并比对 SHA256，通过后同步 `scores/`、`data.json`、`storage-manifest.json`、本地数据库，以及首页 `logs.json`。
6. 每个新增发布批次要有独立首页更新记录，数量按实际新增文件/条目计算；不要混用作品数、文件数和 PDF 页数。这是此前哈恩上传遗漏后用户特别要求的事项。
7. 检查旧目录、旧动态和原投稿未被改坏，运行适当测试和目录/存储一致性检查。
8. 按既有授权，只提交本批新 PDF 及必要的 `data.json`、`logs.json`、`storage-manifest.json`；正常推送 main，等待 GitHub Pages 部署成功。不能把未提交的其他开发工作顺带提交，不能强推或重置用户改动。
9. 比对线上 JSON，检查列表/搜索、单曲或册号标题、调性、中文标记、详情、预览/下载和首页动态；完成后才在本批 `publication.json` 设置 `website_status=verified_live`。
10. 更新续传交接并报告实际新增数量。失败或等待时保存准确断点，不宣称完成，不盲目重新上传整个批次。
